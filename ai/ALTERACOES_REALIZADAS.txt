----------------------------------------------------------------------------------------------
1. RESUMO GERAL DO TRABALHO
----------------------------------------------------------------------------------------------

Estado inicial: a "integração" com o banco NÃO funcionava e o erro era invisível.
  - script_db.js terminava sem exportar nenhuma função e tinha um erro de execução
    (require('dotenv').config([quiet.true]) -> "ReferenceError: quiet is not defined").
  - server.js carregava esse arquivo dentro de um try/catch que engolia o erro em silêncio e
    caía em funções falsas (listar devolvia [], salvar devolvia o próprio objeto recebido).
  - O front-end guardava os Pokémon só na memória do navegador: ao recarregar a página, tudo
    se perdia. Nenhuma chamada ao servidor era feita.
  - schema.sql tinha SQL inválido e não tinha coluna para o tipo do Pokémon.

Estado final: o baralho é lido, gravado, atualizado e removido no PostgreSQL (Neon) através de
uma API HTTP validada; o front-end carrega e grava via API; erros de banco aparecem de forma
clara (log do servidor + mensagem na tela) em vez de serem escondidos; o limite de 12 Pokémon e a
unicidade do nome são garantidos de forma atômica; há migração segura e 33 testes automatizados.


----------------------------------------------------------------------------------------------
2. ARQUITETURA ENCONTRADA
----------------------------------------------------------------------------------------------

Aplicação pequena, SEM framework, em Node.js (CommonJS), 100% "flat" (arquivos na raiz):

  index.html + style.css + script.js   Front-end estático (formulário de cadastro, cards).
  server.js                            Servidor HTTP nativo (módulo http): serve os 3 estáticos
                                       e expõe /api/baralho (GET e POST).
  script_db.js                         Camada de dados (Neon via fetch no endpoint HTTP /sql).
  schema.sql                           Definição da tabela "baralho".
  package.json                         Única dependência: dotenv. Sem script "start" (embora o
                                       README mandasse usar "npm start").
  .env                                 Vazio.

Tecnologias: Node 22 (testado), dotenv 18, banco PostgreSQL no Neon acessado por HTTP (sem
driver/ORM: usa fetch direto no endpoint https://<host>/sql com o cabeçalho
Neon-Connection-String). Integração externa: PokéAPI (consultada pelo NAVEGADOR em script.js
para validar o nome, obter tipos, imagem e poder base).

Não existiam: controllers/services/models separados, middlewares, autenticação, autorização,
migrations, seeders, testes, build. Não há relacionamentos entre tabelas: o domínio inteiro é
uma única entidade (Pokémon do baralho).

Regras de negócio já presentes no código original e preservadas:
  - nome com ao menos 3 caracteres; poder >= 100; nome não repetido (sem diferenciar
    maiúsculas); Pokémon precisa existir na PokéAPI;
  - cards ordenados por poder e o de maior poder recebe a coroa (campeão);
  - LIMITE_BARALHO = 12 (constante que já existia em script_db.js mas nunca foi aplicada).

--- O que foi implementado em cada arquivo ---

script_db.js (camada de dados / "repository")
  - Lê DATABASE_URL (e opcionalmente NEON_HTTP_ENDPOINT) a cada uso; valida formato
    (postgres/postgresql, host, usuário, banco) sem nunca imprimir o valor.
  - Envia as consultas por HTTP ao Neon exatamente como o driver oficial: cabeçalhos
    Neon-Connection-String, Neon-Raw-Text-Output, Neon-Array-Mode; transações em lote com
    Neon-Batch-Isolation-Level: ReadCommitted. Timeout de 20 s.
  - Converte resultados (inteiros/booleanos) por OID do Postgres, sem depender de conversão
    implícita do servidor.
  - ErroBanco com "tipo" (CONFIG, CONEXAO, ESTRUTURA, CONSULTA, NAO_ENCONTRADO, DUPLICADO,
    LIMITE) e SQLSTATE: 23505 -> DUPLICADO; 42P01/42703 -> ESTRUTURA; classes 08/28/57 ->
    CONEXAO. Nunca devolve null/[] para esconder falha.
  - Redige (mascara) a string de conexão e a senha de qualquer texto de erro vindo do banco.
  - Funções: listarBaralho, contarBaralho, buscarPokemonBaralho, salvarPokemonBaralho,
    atualizarPokemonBaralho, removerPokemonBaralho, verificarBanco, executarQueryNeon,
    executarTransacaoNeon. Todas com parâmetros $1, $2... (nenhuma concatenação de valores).
    Na atualização, os nomes das colunas vêm de uma lista fixa interna, nunca do cliente.
  - salvarPokemonBaralho roda em UMA transação: (1) pg_advisory_xact_lock; (2) INSERT condicionado
    a "total < 12" e "nome ainda não existe"; (3) SELECT de diagnóstico para informar se a
    recusa foi por LIMITE ou DUPLICADO. O lock é liberado no commit/rollback; por ter escopo de
    transação, é compatível em princípio com poolers em modo transação (não verificado no Neon real).

server.js (rotas / "controller")
  - Remove o try/catch silencioso e as funções falsas.
  - Rotas: GET /api/saude; GET e POST /api/baralho; GET, PUT, PATCH e DELETE /api/baralho/:id.
  - Status HTTP: 200/201, 400 (validação / JSON inválido / id inválido), 404, 405, 409
    (duplicado / limite), 413 (corpo > 100 KB), 503 (banco indisponível ou não configurado),
    500 (demais). Mensagens ao cliente nunca trazem host, usuário ou credenciais; o detalhe
    técnico vai só para o log do servidor.
  - Carrega o dotenv no início (PORT passa a respeitar o .env), trata erro de leitura de
    arquivo estático, adiciona cabeçalho X-Content-Type-Options e Cache-Control: no-store na API.
  - Na partida, faz um diagnóstico explícito do banco e registra "Conexão OK (n/12)" ou a causa
    da falha. Sem banco, o servidor continua servindo a página e a API responde 503.
  - Encerramento limpo (SIGINT/SIGTERM). Exporta criarServidor() para os testes.

validacao.js
  - nome 3-50 caracteres (letras, números, espaço, . ' ’ : -); treinador opcional, até 50, sem
    caracteres de controle; poder inteiro entre 100 e 2.147.483.647 (limite da coluna INT);
    tipos: até 3 nomes minúsculos; imagem: URL http(s) opcional de até 500 caracteres; id:
    inteiro positivo. Campos editáveis na atualização: apenas treinador e poder.

migrate.js
  - Executa o schema.sql instrução por instrução, informando cada uma; para no primeiro erro.
  - Depois confere a estrutura REAL da tabela baralho (tipos das colunas, id com valor
    automático, colunas extras NOT NULL sem padrão) e lista incompatibilidades. Não altera
    nem apaga nada além do que o schema.sql (aditivo) define.

script.js (front-end)
  - Ao abrir a página, carrega o baralho de GET /api/baralho (dados do banco).
  - Cadastro: mantém todas as validações e a consulta à PokéAPI e passa a gravar por POST
    /api/baralho; só mostra o card depois que o banco confirma. Erros do servidor (duplicado,
    limite de 12, banco fora do ar) aparecem no campo de feedback. Botão de enviar fica
    desabilitado durante a gravação.
  - Remoção: o botão "x" chama DELETE /api/baralho/:id e só então remove o card.
  - Segurança: função escaparHTML aplicada a todo texto vindo do banco; o onclick inline foi
    trocado por addEventListener (identificação por id, não por nome).
  - Pequenos ajustes: imagem usa sprite padrão como alternativa se faltar a "official-artwork";
    poder decimal é recusado com mensagem. Aparência (HTML/CSS) inalterada.

6. CONFIGURAÇÃO DA CONEXÃO COM O BANCO DE DADOS (somente nomes)
----------------------------------------------------------------------------------------------

  DATABASE_URL         OBRIGATÓRIA. String de conexão no formato postgresql://usuario:senha@host/banco
                       (a mesma variável que o projeto original já usava). Nenhum valor foi lido,
                       copiado ou alterado por mim.
  PORT                 Opcional (padrão 3002).
  NEON_HTTP_ENDPOINT   Opcional, SÓ para testes/proxy local. Em uso normal NÃO definir: o endpoint
                       é derivado de DATABASE_URL como https://<host>/sql.

Gestão de conexões: o Neon por HTTP é sem estado (cada chamada é independente), por isso NÃO há
pool a configurar, não existem conexões duplicadas/vazando e não há conexão a encerrar no
shutdown. Justificativa para manter essa tecnologia em vez de trocar por "pg": é a escolha do
projeto, funciona sem dependências extras e suporta transações por lote.

O dotenv é carregado com override desligado (padrão): variáveis já definidas no ambiente do
sistema nunca são sobrescritas pelo arquivo .env.

7. MODELS, TABELAS E RELACIONAMENTOS
----------------------------------------------------------------------------------------------

Uma única tabela, "baralho", sem chaves estrangeiras (o domínio não tem outras entidades):

  id           INTEGER  GENERATED ALWAYS AS IDENTITY, PRIMARY KEY
  nome         VARCHAR(50)  NOT NULL
  combatPower  INT          NOT NULL, CHECK (>= 100)   (no Postgres a coluna se chama "combatpower")
  img          TEXT         NOT NULL
  treinador    VARCHAR(50)  NOT NULL                   (vazio "" quando não informado)
  tipos        TEXT         NOT NULL DEFAULT ''        (NOVA; lista separada por vírgula: fire,flying)
  índice único baralho_nome_unico em lower(nome)       (NOVO)

Mapeamento banco -> API/front-end: combatPower -> "poder", img -> "imagem", tipos -> lista
["fire","flying"]. Não existe model/ORM; o mapeamento é feito em linhaParaPokemon().

Justificativa dos acréscimos: a coluna "tipos" é exigida pelo próprio front-end (cor do card e
texto "Tipo:"), que antes não tinha onde persistir essa informação. Foi guardada como texto
separado por vírgula (e não array do Postgres) para trafegar com segurança como parâmetro simples
no endpoint HTTP. O índice único é a segunda barreira de integridade para o requisito
"nome não repetido" que o front-end já aplicava.

8. MIGRATIONS E ALTERAÇÕES ESTRUTURAIS
----------------------------------------------------------------------------------------------

Comando: npm run migrate   (NÃO é executado automaticamente ao iniciar o servidor).

O schema.sql contém apenas 3 instruções, todas idempotentes e NÃO destrutivas:
  1. CREATE TABLE IF NOT EXISTS baralho (...)
  2. ALTER TABLE baralho ADD COLUMN IF NOT EXISTS tipos TEXT NOT NULL DEFAULT ''
  3. CREATE UNIQUE INDEX IF NOT EXISTS baralho_nome_unico ON baralho (lower(nome))

Nenhuma instrução apaga tabela, coluna, linha ou dado. Pontos de atenção (documentados antes de
executar, como solicitado):
  - Se a SUA tabela baralho já existe e tem registros, os registros antigos ficarão com tipos = ''
    (o card aparece com a cor cinza padrão). Nada é perdido.
  - Se existirem nomes repetidos (ignorando maiúsculas/minúsculas) na sua tabela, a instrução 3
    FALHA com mensagem explicando; nada é apagado. Corrija os duplicados manualmente e rode de novo.
  - Se a estrutura real for diferente da esperada (ex.: id do tipo texto, coluna combatPower criada
    com aspas, coluna extra obrigatória), o migrate informa cada divergência e termina com erro,
    sem alterar a tabela. Nesse caso me informe a estrutura para adaptarmos o código.
  - Em tabelas criadas ANTES desta alteração, o CHECK (combatPower >= 100) NÃO é adicionado
    retroativamente (só vale para a tabela criada pelo schema.sql novo).

Não foram criados seeders (não há dados de domínio que precisem ser pré-carregados).

9. ROTAS, CONTROLLERS E SERVICES INTEGRADOS
----------------------------------------------------------------------------------------------

(Arquitetura flat mantida: server.js = rotas/controllers; script_db.js = repositório/serviço de
dados; validacao.js = validação.)

  GET    /api/saude         verifica conexão e existência da tabela -> {banco:"ok", total, limite}

  GET    /api/baralho/:id   consulta um                                       -> 200 | 404
  PUT/PATCH /api/baralho/:id atualiza treinador e/ou poder                    -> 200 | 400 | 404
  DELETE /api/baralho/:id   remove                                            -> 200 | 404

Mudanças de comportamento a observar: o POST agora responde 201 (antes 200) com o registro
completo, inclusive o "id"; falhas de banco agora respondem 503/500 (antes a API devolvia lista
vazia silenciosamente).

 - Estrutura de arquivos plana preservada; só foi criado módulo novo onde havia necessidade real
